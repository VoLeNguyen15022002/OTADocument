Tài liệu cô đọng, thực chiến về thiết kế và gỡ lỗi Flash Bootloader trên vi điều khiển nhúng & ECU ô tô: từ phần cứng Flash, linker script, vector table, UDS/CanTp, cho đến Dual-Bank rollback và Secure Boot bằng HSM.

1. Ràng buộc phần cứng bộ nhớ Flash

1.1 Erase-before-Write, Độ mịn Xóa/Ghi & ECC

  • Flash không cho ghi đè trực tiếp từng byte như RAM — phải xóa về 0xFF trước khi ghi mới.
  • Erase Sector luôn lớn hơn nhiều so với Write Page / Phrase (ví dụ sector 16 KB, page 32 byte có ECC). Để nạp App 50 KB cần xóa tối thiểu 4 sector = 64 KB.
  • Padding & ECC: Mảnh cuối lẻ (ví dụ 10 byte) phải đệm (pad) thêm 22 byte (thường bằng 0xFF) trong buffer để ghi đủ nguyên page 32 byte. Ghi đè 2 lần vào cùng page chưa xóa trên Flash có ECC sẽ gây lỗi ECC ngay lập tức.

1.2 Same-Bank RWW & HIS Flash Driver trên RAM

  • Một bank Flash vật lý không thể vừa xóa/ghi vừa phục vụ instruction fetch trên cùng bank đó.
  • Trên MCU multi-bank (như TC397 có PF0–PF5), CPU chạy ở PF0 có thể xóa PF1; nhưng trên single-bank hoặc xóa cùng bank, chạy hàm xóa từ Flash sẽ gây đứng CPU / BusFault.
  • Giải pháp (HIS Flash Driver): Tải và chạy Flash Driver từ RAM (SRAM / PSPR):
    1. Lợi ích phần cứng: CPU fetch lệnh từ RAM, không đụng bank Flash đang bận.
    2. Lợi ích an toàn: Flash Driver không tồn tại trong Flash lúc xe chạy ngoài đường, ngăn code lỗi (runaway code) vô tình xóa firmware ECU.
Cảnh báo về Read-Modify-Write qua RAM Đọc sector 16 KB ra RAM → sửa 1 byte → xóa sector → ghi lại sẽ mất trắng toàn bộ 16 KB nếu rút ắc quy đúng lúc vừa xóa xong (kể cả Retention RAM cũng mất khi mất nguồn chính). Với dữ liệu metadata quan trọng, phải dùng 2 sector Flash (Ping-Pong / A-B).

2. Memory Layout & Chuỗi khởi động (Boot Sequence)

2.1 Phần cứng làm gì khi Reset (Cortex-M)

Địa chỉ đầu FlashVí dụHành động phần cứng CPU
0x080000000x20005000Nạp vào MSP (Main Stack Pointer — đỉnh stack trong SRAM)
0x080000040x08000199Nạp vào PC (Reset Vector — địa chỉ Reset_Handler, bit 0 = 1 cho Thumb)
 
POR / Soft Reset
  ├─► Hardware đọc MSP tại 0x08000000
  ├─► Hardware đọc Reset Vector tại 0x08000004 → nạp PC
  ├─► Reset_Handler: copy .data (Flash → RAM), zero .bss, gọi SystemInit() (clock)
  └─► main() của FBL bắt đầu chạy
Tại sao xóa nhầm Sector 0 làm ECU bị Brick? Flash vừa xóa chứa toàn 0xFF → CPU đọc MSP = 0xFFFFFFFF và PC = 0xFFFFFFFF → fault ngay lập tức, mà HardFault vector cũng là 0xFFFFFFFF → CPU rơi vào Lockup. Chỉ cứu được bằng BootROM (BOOT0) hoặc nạp lại qua SWD/JTAG/DAP.

2.2 Linker Script & Shared noinit RAM

/* Ví dụ: Flash 256 KB (FBL 32 KB, App 224 KB), RAM 64 KB (Shared noinit 16 byte cuối RAM) */
MEMORY
{
  FLASH       (rx)  : ORIGIN = 0x08008000, LENGTH = 224K
  RAM         (xrw) : ORIGIN = 0x20000000, LENGTH = 0xFFF0
  SHARED_RAM  (rw)  : ORIGIN = 0x2000FFF0, LENGTH = 16
}
  • Phải rebuild App với Linker Script mới: Nạp file .bin cũ (build cho 0x08000000) vào 0x08008000 sẽ khiến mọi địa chỉ tuyệt đối nhảy ngược vào vùng FBL.
  • FBL không "sleep" trong RAM: App được dùng gần như toàn bộ RAM (64 KB − 16 byte = 0xFFF0). Khi cần vào FBL (10 02), App ghi magic flag vào vùng noinit RAM rồi gọi Soft Reset; FBL đọc xong phải xóa cờ ngay.
  • Bảo vệ Sector 0 phải bằng phần cứng: Linker script không có tác dụng lúc runtime. Phải khóa bằng WRP + khóa vĩnh viễn (OTP / RDP Level 2) hoặc tách quyền bằng HSM / TrustZone.

3. Quy trình nhảy từ FBL sang Application (Jump-to-App)

Sau khi xác nhận App hợp lệ (Valid flag / CRC / CMAC và app_sp hợp lệ trong SRAM), thực hiện đúng thứ tự:

  1. __disable_irq() đầu tiên — khóa ngắt toàn cục để không ngắt nào xen ngang.
  2. Dừng SysTick, tắt & xóa cờ pending NVIC (ICER/ICPR), de-init ngoại vi & trả clock về HSI — tránh ngắt sót từ FBL và tránh treo PLL trong SystemInit() của App.
  3. Cập nhật SCB->VTOR = APP_ADDR (kèm __DSB(); __ISB();) — trỏ bảng vector ngắt sang của App.
  4. Cập nhật MSP = app_sp rồi nhảy ngay sang app_reset (nên viết bằng inline assembly để không đọc biến từ stack sau khi vừa đổi MSP).
  5. App tự gọi __enable_irq() sau khi khởi tạo xong vì PRIMASK vẫn giữ trạng thái tắt sau cú nhảy.
#define APP_ADDR 0x08008000UL

__attribute__((noreturn))
void fbl_jump_to_app(void)
{
    uint32_t app_sp    = *(volatile uint32_t *)(APP_ADDR);
    uint32_t app_reset = *(volatile uint32_t *)(APP_ADDR + 4UL);

    __disable_irq();

    SysTick->CTRL = 0;
    SysTick->LOAD = 0;
    SysTick->VAL  = 0;

    for (uint32_t i = 0; i < 8; i++) {
        NVIC->ICER[i] = 0xFFFFFFFFUL;
        NVIC->ICPR[i] = 0xFFFFFFFFUL;
    }

    fbl_deinit_peripherals_and_clock();

    SCB->VTOR = APP_ADDR;
    __DSB();
    __ISB();

    __asm volatile (
        "msr msp, %0 \n"
        "bx  %1      \n"
        : : "r" (app_sp), "r" (app_reset) : "memory"
    );
    for (;;) {}
}

4. Giao thức nạp Firmware (UDS ISO 14229 & CanTp ISO 15765-2)

CanTp (ISO-TP) phân mảnh gói tin lớn qua khung CAN 8 byte (hoặc CAN-FD 64 byte) với cơ chế Flow Control. Chuỗi dịch vụ UDS tiêu chuẩn:

BướcService IDTên dịch vụVai trò
110 03Extended SessionVào phiên mở rộng trên App
227Security AccessMở khóa Seed/Key (nếu cần trên App)
328Communication ControlTắt lưu lượng CAN bình thường
485Control DTC SettingTắt ghi nhận mã lỗi DTC
510 02Programming SessionGhi cờ noinit RAM → Soft Reset vào FBL
627Security Access (FBL)Xác thực quyền nạp trong FBL
731Routine Control (Erase)Xóa các sector Flash vùng App
834Request DownloadKhai báo địa chỉ đích & dung lượng
936Transfer DataTruyền từng block kèm Block Sequence Counter (BSC)
1037Request Transfer ExitKết thúc truyền dữ liệu
1131Routine Control (Check)Kiểm tra CRC, chữ ký, chống downgrade, đánh dấu hợp lệ
1211ECU ResetReset sang App mới
2 quy tắc vàng xử lý sự cố UDS
  • Timeout khi xóa/ghi Flash: FBL trả NRC 0x78 (Response Pending) để chuyển sang bộ đếm P2* (kèm 3E 80 Tester Present).
  • Retry trùng BSC ở dịch vụ 36: Nếu block đó đã ghi xong trước đó, KHÔNG ghi đè lại vào Flash — trả thẳng Positive Response (76 <BSC>). Nếu BSC nhảy sai thứ tự, trả NRC 0x73.

5. An toàn mất điện, toàn vẹn dữ liệu & Rollback

Mô hìnhMất điện giữa chừng (50%)Ứng dụng thực tế
Single-Bank (1 FBL + 1 App) App hỏng nhưng không brick: FBL vẫn nguyên vẹn, từ chối nhảy App và đứng chờ nạp lại qua UDS Nạp tại xưởng dịch vụ / nhà máy
Dual-Bank (1 FBL + Bank A + Bank B) Tự boot lại Bank cũ bình thường OTA ngoài đường

Metadata nguyên tử & Cơ chế Trial / Confirm Rollback

  • 3 trường metadata bắt buộc: SW Version / Sequence Counter (chọn bản mới hơn khi cả A và B hợp lệ) + CRC / SHA-256 (phát hiện sai dù 1 bit) + Valid/Commit Flag (ghi ở bước cuối cùng).
  • Trial & Confirm: Khi boot bản mới Bank B lần đầu, FBL đặt trạng thái TRIAL / PENDING kèm bộ đếm thử (ví dụ max_tries = 3). Nếu Bank B crash và Watchdog reset liên tục về 0, FBL tự rollback về Bank A. Chỉ chính App ở Bank B sau khi tự kiểm tra ổn định mới ghi cờ CONFIRMED.

6. Secure Boot, Chữ ký số & HSM

Cơ chếĐảm bảo thuộc tínhBắt buộc chống chạy code giả?
Chữ ký số (RSA / ECDSA + SHA-256)Authenticity & IntegrityBẮT BUỘC
Mã hóa (AES)Confidentiality (bảo mật IP)Tùy chọn
  • Public Key trên ECU: Private Key giữ offline tại server OEM; ECU chỉ lưu Public Key (lộ Public Key cũng không ký giả được). Không dùng chung Symmetric Key trên mọi xe.
  • Anti-Rollback (Chống hạ cấp): Chữ ký số không chặn được bản v1.0 thật cũ có lỗ hổng → phải dùng Security Counter tăng một chiều lưu trong HSM DFLASH / OTP / eFuse.
  • Secure Boot mỗi lần bật nguồn (HSM CMAC): Ngăn sửa Flash trực tiếp không qua UDS (debugger/exploit). Lúc nạp UDS kiểm tra chữ ký số rồi HSM lưu Golden CMAC; mỗi lần boot HSM tính lại CMAC rất nhanh để đối chiếu trước khi cho chạy App.
